# /commit skill

ローカルの未コミット変更を、リポジトリ標準のコミット粒度・メッセージ規約に従って整理しコミットするための skill。`issue-commit-guidelines.md` (リポジトリルート) を運用ルールの正典とし、本ファイルはそれを AI がコミット時に従う操作手順へ落とし込んだもの。

---

## 大原則

- **1 commit = 1 論理的な変更**
  - 単独で revert できる
  - 単独でビルド・テストが通る
  - 1 行のコミットメッセージで完結に説明できる
- **複数の関心事を 1 コミットに混ぜない**
  - 特に `feat` と `refactor` を同じコミットに入れない
  - フォーマット変更と機能変更を混ぜない
- **物理的な作業順ではなく、変更の意味で区切る**

---

## 実行手順 (AI はこの順で必ず実行する)

### 1. 現状把握 (並列で実行)

以下を並列に実行し、変更全体を把握する。

- `git status` (`-uall` フラグは使わない / 大規模リポでメモリ問題)
- `git diff` (unstaged)
- `git diff --staged` (既ステージ済みがあれば)
- `git log -n 10 --oneline` (リポジトリのコミットメッセージ慣習を踏襲するため)

### 2. 論理単位への分割設計

把握した差分を論理単位ごとにグループ化する。典型的な分割軸:

- マイグレーション / スキーマ変更
- 新規モジュール追加 (model / service / component など単位)
- 既存モジュールへの機能追加
- バグ修正
- リファクタリング (機能追加とは必ず別コミット)
- テスト追加
- ドキュメント更新
- 設定 / 依存関係更新

**目安**: 1 コミットあたり差分 100〜200 行が読みやすい。1 サブ ISSUE 内で 3〜7 コミット程度。

### 3. ステージング

- **必ず `git add -p` (パッチモード) を使う**
  - ハンクごとに採否を選び、論理単位だけをステージする
  - 同一ファイル内で複数の関心事が混在する場合は `s` (split) で分割する
  - 分割不能なら `e` (edit) で手動編集する
- **`git add -A` / `git add .` / `git add <dir>` は使わない**
  - 意図しないファイル (`.env`, 認証情報, 大きなバイナリなど) が混入する危険があるため
- 新規ファイル (untracked) は対象を絞ってファイル名指定で `git add <path>` する
- ステージ後に `git diff --staged` で「このコミットに含めるべきもののみが入っているか」を必ず確認する

### 4. コミットメッセージ作成 (Conventional Commits)

```
<type>: <subject>

<body (任意)>
```

**type 一覧**:

| type | 用途 |
|---|---|
| feat | 新機能追加 |
| fix | バグ修正 |
| refactor | 振る舞いを変えない内部改善 |
| test | テスト追加・修正のみ |
| docs | ドキュメントのみ |
| chore | ビルド設定・依存関係など |
| style | フォーマット・空白など |

**subject のルール**:

- 日本語で書く (リポジトリの慣習に合わせる)
- 動詞 + 結果 で書く (例: `feat: メニュー一覧画面を追加`)
- 「WIP」「fix」「update」「修正」など内容のないメッセージは禁止
- 50 文字程度を目安

**body のルール** (必要なときのみ):

- 「なぜ」を書く (「何を」は diff から読める)
- 関連 ISSUE 番号がある場合は `Refs: #<番号>` または `Closes: #<番号>` を入れる

### 5. コミット実行 (ヒアドキュメント方式 必須)

整形崩れを避けるため、必ず HEREDOC でメッセージを渡す。`Co-Authored-By` トレイラーは**必須**。

```bash
git commit -m "$(cat <<'EOF'
<type>: <subject>

<body (任意・複数行可)>

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
EOF
)"
```

**禁止事項**:

- `git commit -m "..."` を 1 行で渡す (改行・引用が壊れる)
- `Co-Authored-By` トレイラーを省略する
- `--amend` を使う (新しいコミットを作るのが原則。ユーザーが明示的に指示した場合のみ可)
- `--no-verify` で pre-commit フックをスキップする (ユーザーが明示的に指示した場合のみ可)
- `--no-gpg-sign` で署名をスキップする (同上)

### 6. コミット後検証

`git status` を実行し、

- 該当変更がコミットされたこと
- 残りの未ステージ変更があれば、次のコミット候補として 2〜5 を繰り返すこと

を確認する。

### 7. 残差分の継続処理

未コミットの変更が残っている場合、論理単位ごとに 2〜5 を繰り返す。すべての変更がコミットされるか、ユーザーが「ここまで」と指示するまで続ける。

---

## pre-commit フック失敗時の対応

1. **絶対に `--amend` で対応しない**: フック失敗時はコミットが「作られていない」ため、`--amend` は前のコミットを書き換えてしまい作業を失う恐れがある。
2. フックの指摘内容を読み、根本原因を直す。
3. 修正したファイルを `git add -p` で再ステージする。
4. **新しいコミットとして** 5 をやり直す。

---

## 機密情報・大容量ファイルのガード

以下が変更に含まれていないか、ステージ前に必ず確認する。含まれている場合はユーザーに警告し、判断を仰ぐ。

- `.env`, `.env.*`, `*.pem`, `*.key`, `credentials.json`, `service-account*.json`
- API キー / トークン / パスワードを含む文字列
- 数 MB を超えるバイナリ / ビルド成果物 / `node_modules` 配下

---

## 例外を許容するケース (ユーザー確認必須)

以下は粒度ルールを超過してもよいが、コミットメッセージの body またはユーザーへの説明で理由を明記する。

- 大規模な自動リネーム / フォーマット適用 (機械的変更)
- 外部ライブラリのバージョンアップに伴う一括修正
- 設計上、原子的にコミットしないと壊れる変更
- スパイク / PoC で分割するとかえってコストが上がる場合

---

## セルフチェック (コミット前に必ず確認)

- [ ] このコミットは 1 つの関心事だけを扱っているか
- [ ] このコミットだけ revert してもビルド・テストが通る状態か
- [ ] `feat` と `refactor` が混ざっていないか
- [ ] コミットメッセージは Conventional Commits 形式で、内容を正確に表しているか
- [ ] subject は動詞 + 結果で書かれているか
- [ ] HEREDOC 方式でメッセージを渡しているか
- [ ] `Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>` トレイラーが入っているか
- [ ] `git add -p` を使い、`git add -A` / `git add .` を使っていないか
- [ ] 機密ファイル (`.env` など) が混入していないか
